# AI PM Transition Annual Execution Plan

## 1. 文档状态

本文件是 `ai_pm_transition/` 的年度执行框架，用于把 `master_plan.md` 中的 12 个月目标转成阶段分布、资源索引、作品集节奏和复盘节点。

本文件从 `mvp_memory/ai_pm_transition/master_plan.md` 派生，不替代 `master_plan.md`。月计划、周计划、日计划、复盘记录和闭环记录不在本文件中生成。

本文件应保持中等稳定。下级 `current_stage.md`、`current_month_plan.md`、`current_week_plan.md` 和 `daily_plan` 由本文件与 `current_status.md` 派生。

课程和资料按资源池使用，不要求全部学完。年度计划只定义阶段优先级、候选资源和调用边界，后续月 / 周计划可按当前问题、时间和产出需要灵活选用或跳过。

执行节奏采用强弱周 / 双周滚动：月度目标保持稳定，强周用于推进学习、练习、Demo 和作品集证据，弱周用于复盘、整理、补缺和恢复；双周中若有休息周，则该周计划应提前降密度。年度计划只定节奏原则，不写固定每日任务。

## 2. 年度执行目标

- 主线从复杂 B2B/B2G 产品背景迁移到 C 端 AI Product Manager / AI-native Consumer Product Manager。
- 保留企业级 / B 端 AI PM 作为备选线。
- 从 Phase 0 的恢复性复习与整合基线开始。
- 让已学产品基础回到可调用状态，而不是重刷课程。
- 建立学习方法论与自我调节能力，让 12 个月训练本身可持续、可复盘、可迁移。
- 通过 AI-assisted prototyping / vibe coding 支持轻量 Web Demo、RAG Demo、Agent / Workflow 原型。
- 中后期完成 3-5 个轻量用户访谈 / Demo 测试。
- 形成至少 1 个完整 AI PM 作品集项目和 1 个轻量备选 demo / case。
- 支持 C 端 AI PM 和企业级 / B 端 AI PM 两种投递叙事。
- 严格区分教学材料和用户学习数据。

## 5. Phase 1：C 端 AI 产品问题发现与概念设计

### 阶段目标

围绕 1 个候选 C 端 AI 产品问题，把问题发现、用户理解、AI 适用性判断和低保真概念设计放在同一任务中训练。

### 完整任务主线

```text
Codex 扩展候选 product idea 池 → 用户选择主练习问题 → 定义目标用户和使用场景 → 做访谈准备和竞品观察 → 写低保真 product brief / PRD → 拆 Backlog / 用户故事 / AC → 判断 AI 适用性和兜底边界
```

主线方向仍是 AI 学习 / 个人成长、AI 求职 / 职业规划 / 复盘、AI 个人效率 / Workflow / Agent、AI 搜索 / 知识消费；AI 陪伴 / 社交 / 娱乐互动只作观察。

### 产品 idea 池与选择机制

Phase 1 将 Phase 0 的 idea 扩展到 10-15 个可实践候选，用户选 1 个主练习问题、保留 2-3 个备选。每个 idea 只保留一句话概念、目标用户、场景、问题、AI 介入方式、MVP 范围和风险。

### 已学内容处理原则

49 天已学内容在 Phase 1 只作为“应用和回查”来源，不作为系统课程重复学习。`数字产品管理：现代基础知识`、`敏捷与设计思维的结合` 放入 Phase 0 回查与复习；`假设驱动的开发`、`产品分析和人工智能`、`管理敏捷团队` 放入 Phase 1 完整学习。Duke / Coursera `AI Product Management Specialization` 仍保留在 Phase 3 备选课程，不进入 Phase 1 主课程。

## 6. Phase 2：用户体验、指标与轻量验证方案

### 阶段目标

把 Phase 1 的候选问题推进到用户体验、指标和轻量验证层，判断目标用户是否能在关键流程中顺利完成任务、是否需要调整方案，以及哪些验证足以进入 Phase 3 的 AI 小实验。

### 完整任务主线

```text
候选问题与 brief → 用户旅程 / Onboarding / 关键流程拆解 → 指标与验证假设 → 轻量验证方案 → 原型或流程图 → Phase 3 AI 小实验输入
```

### 重点能力

- C 端用户体验、旅程和关键流程拆解。
- Onboarding、激活、留存和信任点识别。
- 指标与验证假设连接。
- 定性 / 定量验证方式选择。
- 从概念走向可验证的轻量原型。

### 关键练习

- 拆解一个候选问题的核心流程和掉线点。
- 为候选产品写 3-5 个指标，并说明每个指标验证什么。
- 把 Phase 1 的 brief 改写成轻量验证方案。
- 比较 2 种验证方式的成本、信息量和风险。
- 画一版低保真原型或关键流程图。

## 11. 年度作品集推进节奏

- Phase 0：只复盘，不正式启动作品集。
- Phase 1：形成问题定义和基础产品文档练习。
- Phase 2：形成 C 端用户和产品机会判断。
- Phase 3：形成 AI 小实验和 eval 基础。
- Phase 4：推进主作品集 Demo 和 eval。
- Phase 5：整理 Portfolio 和求职表达。

作品集证据应逐步形成，不是最后补做。

## 12. 年度复盘节点

- Phase 0 结束复盘
- Phase 1 结束复盘
- Phase 2 结束复盘
- Phase 3 结束复盘
- Phase 4 中期和结束复盘
- Phase 5 年度总结

每个复盘点检查：能力、证据、资源、学习方法是否有效、作品集方向、`current_status` 是否需要更新、是否需要提出 `master_plan` 更新建议。

## 13. 年度边界规则

- 不修改 `training_14day/`
- 不继承 14 天训练完成事实
- 不直接生成月计划、周计划、日计划
- 不创建复盘、评价、闭环记录
- 不创建代码、脚本、自动化、Skill、API、harness
- 不把资源候选写成已批准必学任务
- 不把作品集候选写成最终确定项目
- 不随意采集用户学习数据
- 不使用盗版或未经授权教学材料
- 不把 `codex-study-os` 写成已完成 AI Agent

## 14. 与下级计划的关系

- `annual_plan.md` 定义年度框架。
- `current_stage.md` 作为当前阶段运行态文件，从 `annual_plan.md`、`master_plan.md` 和 `current_status.md` 派生。
- `current_month_plan.md` 从 `current_stage.md` 派生。
- `current_week_plan.md` 从 `current_month_plan.md` 和 `current_status.md` 派生。
- `daily_plan` 从 `current_week_plan.md` 和 `current_status.md` 派生。
- `methodologies/methodology_index.md` 负责指导下级计划和备课“如何学、如何练、如何检查”，不记录完成事实，不替代计划文件。
- `review` 更新 `current_status`，不直接改写 `annual_plan` 或 `master_plan`。
- 资源复核结果可以影响 `current_stage` / month / week，但不自动修改 `annual_plan`。
