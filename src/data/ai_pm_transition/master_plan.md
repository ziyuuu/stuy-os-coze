# AI PM 转型 12 个月 Master Plan

## 1. 文档状态

本文件是 `ai_pm_transition/` 工作区的正式 12 个月 Master Plan。

当前版本：V2.0。

本文件定义长期目标、目标定位、能力模块、阶段结构、作品集策略、资源策略、复盘调整规则、材料与数据边界，以及与下级计划的关系。

本文件不是年度计划、阶段计划、月计划、周计划或日计划。下级计划应从本计划派生，并结合 `current_status.md` 中的实际状态滚动生成。

本计划保持相对稳定，不随日常执行频繁改动。只有在阶段性复盘、目标变化、资源环境出现重大变化，或用户明确要求时，才考虑更新本文件。

## 2. 长期目标

在 12 个月内，完成从复杂 B2B/B2G 产品背景向 C 端 AI Product Manager / AI-native Consumer Product Manager 的能力迁移。

12 个月目标包括：

- 能投递 C 端 AI PM / AI-native Consumer PM 岗位，重点面向 AI 学习、个人成长、求职成长、个人效率、Workflow、Agent、AI 搜索和知识消费方向。
- 能投递企业级 AI、B 端 AI、政企数据平台、数据与知识平台、B 端 Agent 相关岗位，作为现实备选线和城市约束下的风险对冲。
- 形成 1 个完整 AI PM 作品集项目，能够展示从问题定义、用户洞察、方案设计、AI 原型、eval、反馈到迭代的闭环。
- 形成 1 个轻量备选 demo / case，用于补充 RAG、AI 搜索、知识消费、企业级知识库或 B 端 Agent 方向的证据。
- 明显补强产品基础，把已学习过的产品方法恢复到可用于真实项目判断、设计、拆解和表达的水平。
- 具备独立或借助 AI-assisted prototyping / vibe coding 完成简单 Web Demo、RAG Demo、Agent / Workflow 原型的能力，但不把训练目标转成传统工程师路线。
- 建立面向求职的表达系统，包括 C 端 AI PM 主线叙事、B 端 / 企业级 AI 备选叙事、主项目讲述稿、Demo 讲述稿和作品集页面。

## 4. 目标定位

### 主线：C 端 AI Product Manager

主线定位是 C 端 AI Product Manager / AI-native Consumer Product Manager。

重点关注方向：

- AI 学习 / 个人成长产品。
- AI 求职 / 职业规划 / 复盘产品。
- AI 个人效率 / Workflow / Agent 产品。
- AI 搜索 / 知识消费产品。
- AI 陪伴 / 社交 / 娱乐互动产品作为观察方向，不作为初期主攻方向。

这条主线对应用户的主观职业目标，需要补强 C 端用户洞察、体验、增长、留存、转化、用户信任和 AI-native 交互设计能力。

### 备选线：企业级 / B 端 AI

现实备选线是企业级 AI、政企数据平台、数据与知识平台、知识库 / RAG、B 端 Agent、AI Workflow 和行业 SaaS + AI。

保留备选线的原因：

- 与用户既有复杂 B2B/B2G、高合规、权限、数据、政企和金融相关背景复用度更高。
- 与长沙本地机会更匹配。
- 与 C 端 AI 主线共享 LLM、RAG、Agent、Workflow、eval、数据治理和 AI 风险边界等能力底座。
- 可作为求职风险对冲，避免目标岗位过窄。

### 城市与工作方式约束

长沙优先，接受远程办公。

因此，C 端 AI PM 主线应重点关注远程机会和可迁移作品集证据；长沙本地机会更可能落在企业级 AI、内容科技、政企数据、行业 AI、B 端 SaaS + AI 等方向。

## 5. 能力模块

本计划不把产品基础、C 端产品和 AI PM 训练拆成三条彼此独立的课程线。AI PM 转型是复杂职业能力学习，应采用“完整任务驱动 + 局部专项补强”的结构：围绕长期主线项目和若干短小 C 端 AI 产品实战题推进，从用户问题、体验设计、AI 方案、Demo、eval、反馈到求职表达逐步形成闭环；当某个局部能力明显不足时，再插入短小、及时、可验证的专项训练。

该设计依据以下学习原则：

- 复杂能力优先用完整任务学习，而不是先长期拆成孤立知识块。
- 交错练习有助于迁移，学习者需要在相近但不同的问题中反复判断该调用哪类知识。
- 情境学习要求知识放回真实使用场景，抽象方法必须服务具体产品任务。
- 初期仍需要脚手架，避免把过多产品、AI、数据、Demo 和求职任务一次性压到同一个练习中。

## 5.1 学习设计原则

本计划采用任务驱动的学习设计，但任务驱动不等于放弃课程、书籍、官方文档和案例的系统性。AI PM 转型属于复杂职业能力学习，下级计划和备课文件应采用以 4C/ID 思路为主的“完整任务主线 + 连贯课程支撑线 + 程序性脚手架 + 局部专项练习”结构。

Master Plan 只保留学习设计原则摘要：

- 完整任务优先：每个阶段、月和周都应围绕可解释的 C 端 AI 产品任务组织，而不是只围绕课程章节组织。
- 小实战题服务完整任务：小实战题用于训练迁移、产品敏感度和工具选择，不替代主线项目。
- 局部专项补强：当完整任务暴露短板时，再插入短小、及时、可验证的专项练习，并回到原任务验证。
- 脚手架递减：前期提供示例、模板、问题清单、反例和检查表，中后期逐步增加用户独立判断。
- 检索练习与间隔复习：恢复旧知识时先回忆、解释和应用，再查漏修正；关键概念在不同任务中反复出现。
- 螺旋递进与交错练习：同一能力在不同复杂度和相近场景中反复调用，训练迁移判断。
- 形成性评价：关键产出必须有检查标准，用于发现缺口和决定下一步补强。
- 目标、任务、资源、证据对齐：资源选择服务能力缺口和产出证据，不以热门程度或课程完成量作为能力标准。
- 认知负荷控制：月、周、日计划不得把产品、AI、代码、eval、用户研究和求职表达一次性压入单日任务。
- 计划与备课分离：计划回答“做什么”，备课回答“如何学、如何练、如何检查”，备课不记录完成事实，也不直接更新 `current_status.md`。
- 学习方法论贯穿后续阶段：Phase 0 之后，每个阶段都应安排少量学习方法论输入和应用练习，像之前学习原子习惯一样，把方法直接用于当前 AI PM 训练，而不是把学习方法论做成独立读书任务。

学习设计细则、4C/ID 四类要素、小实战题规则、备课边界、形成性评价规则和 Phase 1-5 学习方法论安排见 `methodologies/methodology_index.md`。

## 6. 12 个月阶段结构

本计划采用 Phase 0-5 结构，但阶段不是“产品基础课 → C 端课 → AI 技术课”的分科顺序。每个阶段都围绕 C 端 AI 产品任务推进，只是任务复杂度、证据深度和外部验证强度逐步增加。

Phase 0-4 采用统一的 4C/ID 展开结构：阶段目标、完整任务主线、课程支撑线、程序性脚手架、局部专项练习、应形成证据、阶段结束判断和不应做什么。Phase 5 以证据重组和求职表达为主，结构单独处理。

具体起止时间、强弱周安排和每日任务由后续年度计划、阶段计划、月计划、周计划和日计划派生，本文件不绑定具体月份日程。

### Phase 0：恢复性复习与整合基线

阶段目标：

- 恢复 49 天产品学习成果，但不把复习做成孤立课程。
- 盘点旧 Playbook、长期学习系统、课程笔记、Gemini 产出和学习图书馆。
- 判断旧 Notion “长期学习系统”、`codex-study-os` 和 `ai_pm_transition/` 的关系。
- 用 1-2 个 C 端 AI 产品场景样例，建立“产品问题 + C 端用户 + AI 可能性 + 证据缺口”的整合基线。
- 采用“快速回顾旧模块 → 检索练习 → C 端 AI 小场景应用 → 发现断点 → 局部回补资源”的恢复方式，避免把 Phase 0 做成单纯重读或完整重刷课程。
- 做 1-2 个低复杂度小实战题，用于恢复产品判断、旧知识检索和能力缺口识别。
- 建立后续小实战题池的来源、题型和使用规则，但不生成具体题库。

主要能力：

- 产品基础回忆与归纳。
- 旧成果审计。
- 产品文档质量判断。
- C 端 AI 场景识别。
- 产品、C 端、AI 和 eval 缺口的整合判断。

关键学习内容：

- Inspired / 《启示录》中的产品发现与 PM 角色。
- The Mom Test 中的访谈原则。
- Lean Product / Lean Startup / PMF / MVP。
- JTBD、HEART、PRD、Backlog、用户故事、Acceptance Criteria、Roadmap。
- 旧长期学习系统 PRD、Backlog、路线图和 Playbook 的复盘。
- C 端 AI 学习 / 个人成长、AI 个人效率、AI 搜索 / 知识消费场景的初步样例观察。

应形成的证据：

- 49 天学习复习摘要。
- Playbook 复盘版或缺口清单。
- 长期学习系统复盘。
- `study-os` 当前能力说明。
- 整合能力缺口清单：产品判断、C 端用户、AI 技术理解、eval、Demo、求职表达分别缺什么。
- 1-2 个 C 端 AI 产品场景的一页纸问题简报。
- 1-2 个小型 C 端 AI 产品实战题的检索练习记录。

不应做什么：

- 不启动正式主作品集项目。
- 不做正式用户访谈。
- 不把旧长期学习系统直接确认为主项目。
- 不把复习变成重刷课程。
- 不创建日计划执行系统。
- 不修改 `training_14day/`。

### Phase 1：C 端 AI 产品问题发现与概念设计

阶段目标：

- 围绕一个候选 C 端 AI 产品问题，把产品基础、C 端用户理解和 AI 适用性判断合在同一任务中训练。
- 建立小实战题池，用短小 C 端 AI 产品题训练产品敏感度、迁移判断和工具选择，不把训练量完全压在主线项目上。
- 产出低保真的产品概念，而不是只做产品方法练习。

主要能力：

- 问题定义。
- 用户访谈准备。
- 需求分析。
- 竞品分析。
- MVP 验证。
- AI 是否适合该问题的判断。
- C 端体验和信任风险识别。
- 指标设计。

关键学习内容：

- 产品发现与机会判断。
- 用户访谈和用户问题识别。
- JTBD 与场景拆解。
- MVP、PMF 和验证性学习。
- PRD、Backlog、用户故事和 AC。
- HEART、AARRR、North Star Metric 和基础产品指标。
- AI 学习、求职成长、个人效率、AI 搜索和知识消费产品的竞品观察。
- AI 输出不确定性、用户信任和失败兜底的基本判断。
- 学习方法论：习惯设计、身份型习惯、环境提示和最小行动，用于恢复稳定学习节奏并降低启动阻力。

应形成的证据：

- 一个 C 端 AI 产品候选问题定义。
- 目标用户假设和使用场景。
- 用户访谈提纲。
- 低保真 PRD / product brief。
- Backlog / 用户故事 / AC 初稿。
- 指标设计。
- 低保真原型或流程图。
- AI 适用性说明：为什么需要 AI、哪里不该用 AI、失败时如何兜底。
- 阶段学习习惯设计说明：本阶段如何用最小行动、固定触发器和复盘机制维持学习。

不应做什么：

- 不把产品基础练习和 AI 判断分开做成两份互不相关作业。
- 不把所有训练锁死在单一 Agent 项目上。
- 不把课程学习本身当成能力证据。
- 不生成固定每日学习表。
- 不在用户假设不清楚时做复杂 Demo。

### Phase 2：体验、指标与轻量验证方案

阶段目标：

- 在 Phase 1 的候选问题上深化 C 端体验、指标、Onboarding、用户信任和轻量验证方案。
- 开始把 AI 交互、模型输出质量和用户行为指标放进同一套验证设计。

主要能力：

- C 端用户研究。
- UX / 交互设计基础。
- 用户行为分析。
- 激活、留存、转化。
- Funnel / Cohort。
- A/B 测试方案。
- Onboarding 和用户信任设计。
- C 端 AI 产品机会判断。
- AI 输出质量指标和用户体验指标连接。

关键学习内容：

- C 端用户画像和用户旅程。
- 可用性测试与交互体验。
- 内容产品、创作者工具、个人效率产品、学习 / 教育 / 个人成长产品案例。
- 用户信任、AI 输出可解释性和用户控制。
- 订阅、付费转化和商业化基础。
- AI 产品中的多状态体验：正常输出、低置信度、错误、拒答、人工接管、用户纠错。
- 学习方法论：刻意练习、反馈循环和错题 / 案例复盘，用于把用户研究、指标和体验判断练成可迁移能力。

应形成的证据：

- C 端 AI 竞品拆解。
- 用户画像。
- 用户旅程。
- Onboarding 分析。
- Funnel / Cohort 模拟分析。
- 增长实验设计。
- 轻量验证方案。
- AI 输出质量和用户体验指标草案。
- 中保真原型或关键交互流程。
- 关键能力刻意练习记录：至少说明一个短板、练习方式、反馈来源和修正结果。

不应做什么：

- 不只关注 B 端业务流程而忽略 C 端体验。
- 不在没有目标用户假设时启动正式访谈。
- 不把 AI 陪伴 / 社交 / 娱乐互动提前作为主攻项目。
- 不把增长指标和 AI 输出质量分开设计。

### Phase 3：AI 能力实验与 Eval 设计

阶段目标：

- 针对前两个阶段定义的 C 端 AI 产品任务，做最小必要 AI 实验。
- 用 Prompt、RAG、Agent / Workflow 和 eval 小实验验证 AI 方案是否可行。
- 建立作品集项目所需的技术理解和评估底座。

主要能力：

- LLM 基础。
- Prompt Engineering。
- Context Engineering。
- RAG 和 Embedding。
- Vector DB 基础。
- Agent / Tool Calling / Workflow。
- AI Chat UX。
- AI 输出质量评估。
- 成本、延迟、稳定性、失败兜底和安全边界。

关键学习内容：

- OpenAI、Anthropic、Gemini 等模型能力和工具调用概念。
- RAG 流程、知识库、引用和来源意识。
- Agent 任务拆解、工具调用、记忆和人工审核边界。
- eval 测试集、rubric、输出质量、幻觉和遗漏。
- AI 产品中用户信任、可解释性和失败兜底。
- AI 原型与产品假设的对应关系：每个技术实验必须回答一个产品问题。
- 学习方法论：复杂技术概念的学习策略、费曼解释、类比建模和实验笔记，用于避免只会照做教程而不会产品化判断。

应形成的证据：

- 针对候选产品任务的 Prompt 对比实验。
- 针对候选产品任务的 RAG 小 Demo。
- 针对候选产品任务的 Agent / Workflow 小实验。
- eval 测试集。
- rubric。
- 输出质量评估报告。
- AI 交互失败兜底设计。
- 技术方案取舍说明：为何选 Prompt / RAG / Agent，何时不用。
- 技术概念解释记录：用自己的话解释一个关键 AI 技术概念及其产品边界。

不应做什么：

- 不把 AI 技术学习变成传统工程师路线。
- 不跳过实验只学习理论。
- 不对模型输出黑箱化处理。
- 不使用真实敏感数据做 Demo。
- 不做与产品任务无关的技术玩具实验。

### Phase 4：作品集项目闭环实践

阶段目标：

- 形成至少 1 个主作品集项目。
- 使用低代码、AI-assisted prototyping 或 vibe coding 做可运行 Demo。
- 在中后期进行 3-5 个轻量用户访谈 / Demo 测试。
- 把用户问题、C 端体验、AI 原型、eval、反馈和迭代整合成一个可讲述项目。

主要能力：

- 产品发现到 Demo 的闭环。
- AI 产品方案设计。
- C 端体验设计。
- RAG / Agent / Workflow 原型化。
- eval 与用户反馈。
- 迭代记录。

关键学习内容：

- 主项目问题定义和目标用户假设。
- PRD、原型、系统 / Agent 设计。
- Demo 范围控制。
- 测试集、rubric 和 eval 报告。
- 轻量用户反馈和迭代。
- 作品集证据整理。
- 学习方法论：项目制学习、能量管理、范围控制和阶段性收敛，用于把长期项目推进到可展示证据，而不是无限扩展。

应形成的证据：

- 项目 PRD。
- 系统 / Agent 设计。
- 交互原型。
- 可运行 Demo。
- 测试集。
- eval 报告。
- 3-5 个轻量用户反馈。
- 迭代记录。
- Demo 视频或展示说明。
- 项目决策日志：用户问题、体验取舍、AI 方案、eval 结果和迭代理由。
- 项目推进复盘：记录一次范围取舍、一次能量 / 时间管理调整和一次基于反馈的学习方式调整。

不应做什么：

- 不把项目写成已最终确定。
- 不追求工程级复杂系统。
- 不只做效果截图。
- 不在没有授权时展示用户可识别反馈。
- 不将 `codex-study-os` 写成已完成 AI Agent。
- 不把 PRD、Demo、eval、用户反馈拆成互不关联的材料。

### Phase 5：作品集整理与求职表达

阶段目标：

- 把学习和项目证据转化为求职材料。
- 同时服务 C 端 AI PM 主线和企业级 / B 端 AI 备选线。

主要能力：

- 作品集信息架构。
- 项目讲述。
- Demo 演示。
- 简历和岗位匹配。
- 面试故事。
- C 端与 B 端叙事切换。

关键学习内容：

- Portfolio 页面结构。
- 主项目讲述稿。
- Demo 讲述稿。
- C 端 AI PM 简历表达。
- B 端 / 企业级 AI 备选简历表达。
- 岗位匹配矩阵。
- 面试 case 复盘。
- 学习方法论：反思性实践、知识外化、叙事化表达和面试前检索练习，用于把学习过程转化为可讲述的能力证据。

应形成的证据：

- Portfolio 页面。
- 主项目讲述稿。
- C 端 AI PM 简历版本。
- B 端 / 企业级 AI 备选简历版本。
- 面试故事库。
- 岗位匹配清单。
- Demo 展示脚本。
- 个人学习方法复盘：总结 12 个月中最有效、无效和需要保留的学习原则，并沉淀为后续职业学习系统。

不应做什么：

- 不在最后阶段才补作品集证据。
- 不临时堆砌课程证书替代项目证据。
- 不把备选线写成主线替代。

## 7. 作品集策略

12 个月内形成 1 个主作品集项目和 1 个轻量备选 demo / case。作品集必须证明 AI PM 的闭环能力，而不是只展示 PRD、截图或 AI 效果。

主项目候选仍是 `codex-study-os` / AI 学习成长 Agent，但不得写成已完成 AI Agent，也不得在本文件中写成最终确定项目。如果后续选择它作为主项目，必须逐步从自用系统走向可展示产品证据，包括目标用户、用户问题、C 端体验、可运行 Demo、eval、测试集、rubric、轻量反馈和迭代记录。

轻量备选 demo / case 方向保持不变：AI 搜索 / 知识消费 / RAG Demo、企业级知识库 / RAG Demo、B 端业务流程 Agent / Workflow case、数据与知识平台轻量产品方案。备选线用于补充 RAG、知识材料处理、引用来源意识、eval、测试集和企业级 / B 端 AI 证据。

作品集评价以证据闭环为核心：问题是否真实清晰，目标用户和场景是否明确，AI 是否服务用户任务，Demo 是否证明核心价值假设，eval 是否发现输出问题，反馈是否授权、匿名化、最小化，迭代是否基于证据，求职表达是否能说明取舍、风险和下一步。

作品集策略、候选项目决策规则、证据链和展示边界细则见 `portfolio/portfolio_plan.md`。

## 8. 资源策略

资源策略遵循：

```text
能力缺口 → 练习任务 → 作品集证据 → 资源选择
```

资源不是独立学习目标，而是支持 AI PM 转型任务的输入材料。资源是否有效，不以“看完”为标准，而以是否能转化为问题判断、产品文档、实验结果、eval 证据、Demo 证据、用户反馈、复盘结论或作品集表达为标准。

不采用：

```text
热门课程 → 学习安排 → 假设能力提升
```

本计划只建立资源候选池和复核机制，不把具体课程、博客、书籍、训练营或工具写成已批准必学清单。资源进入年度计划、阶段计划、月计划或周计划前，需要二次复核。

资源类目包括：已学 / 需复习资源、产品基础稳定资源、C 端产品补强资源、Human-AI Interaction 与 Conversation UX 资源、AI PM / LLM / RAG / Agent / eval 高时效资源、AI 产品分析与运营资源、AI 产品商业化与增长资源、作品集实践资源、岗位 / JD / 面试 / 职业市场资源。

资源候选池和资源进入 4C/ID 学习闭环的细则见 `resources/resource_catalog.md`。资源复核机制、复核节奏、检查项和排除规则见 `resources/resource_review.md`。资源索引和已批准 / 待复核状态汇总见 `resources/resource_index.md`。

## 9. 教学材料与用户数据边界

教学材料、用户学习数据、AI 输出风险和用户信任边界不仅是合规要求，也是 AI PM 转型能力的一部分。对于 AI 学习、求职、个人成长和 Agent 类产品，后续 Demo 与作品集必须说明材料来源、数据最小化、授权、匿名化、AI 输出限制、用户控制、失败兜底和透明度。

Master Plan 保留边界摘要：

- 教学材料必须合法、可引用、可说明来源；不得使用盗版、未经授权课程内容、付费材料全文或把第三方材料伪装成自己的产出。
- 用户学习数据、访谈、Demo 测试和反馈必须授权、最小化、匿名化，并允许撤回；不得收集或展示真实敏感数据和可识别私人信息。
- AI 输出必须提示不确定性、支持查看依据、纠错、追问、忽略建议和人工判断；不得让用户误以为系统具备专业认证能力、绝对正确性或完整个人理解能力。
- 用户信任与透明度必须体现在能力范围说明、数据使用说明、输入可修改、数据可撤回、错误 / 拒答 / 低置信度处理和隐私取舍中。
- 作品集展示必须区分真实反馈、脱敏样例、模拟测试样例、AI 生成样例和作者分析判断；不得把模拟样例伪装成真实用户反馈。

材料、数据、AI 输出风险和用户信任边界细则见 `operating_rules.md`。作品集展示边界细则见 `portfolio/portfolio_plan.md`。

## 11. 复盘与调整规则

Master Plan 保持相对稳定。下级年度、阶段、月、周、日计划可以滚动调整。

复盘原则：

- 日复盘更新 `current_status.md` 或影响后续日 / 周计划，不直接改写 Master Plan。
- 周复盘可提出下周调整建议，不自动改写 Master Plan。
- 月复盘可回顾能力变化、资源有效性、作品集进展和节奏问题，但不直接生成新的长期战略。
- 阶段性复盘可以提出 Master Plan 校准建议，但必须经用户明确要求或批准后才修改本文件。
- 复盘应检查 4C/ID 四类要素：完整任务是否清晰，课程支撑是否服务任务，脚手架是否过强或不足，局部专项练习是否解决真实短板；小实战题是否促进迁移，而不是变成碎片任务。
- 资源复核结果可影响下级计划，但不直接重写总目标。
- 评价意见不得直接写成计划修改，必须经过受控闭环。

节奏原则：

- 下级计划应采用强弱周 / 双周滚动节奏。
- 月度目标保持稳定，周计划根据实际状态调节强度。
- 强周推进学习、练习、Demo 或作品集证据。
- 弱周收敛、复盘、补缺、整理和恢复。
- 双周中有一周的 5、6、7 休息时，周计划应提前降低执行密度。
- 日计划根据 `current_week_plan.md` 和 `current_status.md` 生成，不在 Master Plan 中固定。

Phase 0 结束后，应根据复盘结果校准作品集方向。若 `codex-study-os` 无法从自用系统走向可展示产品证据，应保留为学习承载系统，并选择更适合作品集的主项目。

## 12. 与下级计划的关系

`master_plan.md` 定义长期目标、能力模块、阶段结构、作品集策略、资源策略和边界规则。

下级计划关系如下：

- `annual_plan.md` 从 `master_plan.md` 派生，负责把 12 个月目标转成年度执行框架和阶段优先级。
- `current_stage.md` 从 `annual_plan.md` 和 `master_plan.md` 派生，负责当前阶段目标、能力重点、产出要求和评价方式。
- `current_month_plan.md` 从 `current_stage.md` 派生，负责当前月目标、能力重点、产出和复盘安排。
- `current_week_plan.md` 从 `current_month_plan.md` 和 `current_status.md` 派生，负责本周目标、练习安排、产出和复盘安排。
- `daily_plan` 从 `current_week_plan.md` 和 `current_status.md` 派生，负责当天学习安排。
- 月度、周度和日度备课文件分别从对应计划派生，只说明如何学、如何练、如何检查和使用哪些脚手架，不替代计划文件，不记录完成事实。
- `review` 根据用户明确提供的完成事实、未完成事实、困难和调整建议更新 `current_status.md`。

禁止关系：

- Daily plan 不得直接修改 Master Plan。
- Review 不得直接改写 Master Plan。
- 单次日复盘不得把计划内容写成已完成事实。
- 下级计划不得突破本文件的边界规则。
- 未经复核的资源不得从候选池直接变成必学任务。
- 未经 Phase 0 / Phase 1 复盘的作品集候选不得写成最终项目。
